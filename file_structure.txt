
WEBHOOK DELIVERY SERVICE — FILE STRUCTURE
==========================================

  webhook_delivery/                  <- project root
  |
  |-- app/                           <- main application package
  |   |-- main.py                    <- FastAPI app entry point; mounts routers (/webhooks, /health)
  |   |-- models.py                  <- Pydantic models: IncomingWebhook, DeliveryAttempt, DeliveryStatus enum
  |   |-- config.py                  <- Loads env vars (REDIS_URL, WEBHOOK_SECRET, MAX_RETRY_ATTEMPTS, etc.)
  |   |-- __init__.py
  |   |
  |   |-- routes/                    <- HTTP route handlers
  |   |   |-- webhooks.py            <- POST /webhooks: verify sig -> parse -> idempotency -> enqueue
  |   |   |-- health.py              <- GET /health: simple liveness check
  |   |   |-- __init__.py
  |   |
  |   |-- core/                      <- Business logic (no HTTP, no I/O)
  |   |   |-- security.py            <- verify_signature(): HMAC-SHA256 check on incoming requests
  |   |   |-- idempotency.py         <- is_duplicate() + mark_processed(): Redis SET NX / SET EX
  |   |   |-- retry.py               <- compute_backoff(): exponential + jitter; should_move_to_dlq()
  |   |   |-- __init__.py
  |   |
  |   |-- storage/                   <- External storage adapters
  |   |   |-- redis_client.py        <- Redis connection singleton; lpush/brpop/set wrappers
  |   |   |-- __init__.py
  |   |
  |   |-- workers/                   <- Background processes (run separately from the API)
  |       |-- delivery_worker.py     <- Infinite loop: BRPOP queue -> HTTP POST -> retry/DLQ logic
  |       |-- __init__.py
  |
  |-- tests/                         <- Pytest test suite
  |   |-- conftest.py                <- Shared fixtures (mock Redis, test client, etc.)
  |   |-- test_health.py             <- Tests for GET /health
  |   |-- test_security.py           <- Tests for HMAC signature verification
  |   |-- test_idempotency.py        <- Tests for duplicate detection / TTL behavior
  |   |-- test_retry.py              <- Tests for backoff computation and DLQ threshold
  |   |-- __init__.py
  |
  |-- demo/
  |   |-- index.html                 <- Browser UI to send test webhooks and see responses
  |
  |-- .github/
  |   |-- workflows/
  |       |-- ci.yml                 <- GitHub Actions: runs pytest on push/PR
  |
  |-- Dockerfile                     <- Builds the FastAPI + worker image
  |-- docker-compose.yml             <- Brings up app + Redis together
  |-- requirements.txt               <- Python dependencies (FastAPI, uvicorn, redis, httpx, etc.)
  |-- .env.example                   <- Template for required environment variables
  |-- .gitignore
  |-- .dockerignore
  |-- generate.py                    <- Helper script to generate sample webhook payloads
  |-- spec.md                        <- Written spec / requirements for the service
  |-- README.md                      <- Project overview and setup instructions
  |-- webhook_delivery.txt           <- ASCII flow diagram of the full request lifecycle


  =============================================
  FOLDER PURPOSES AT A GLANCE
  =============================================

  app/routes/    HTTP boundary — only knows about requests and responses.
                 Delegates all logic to app/core/ and app/storage/.

  app/core/      Pure business logic. No FastAPI, no Redis imports.
                 Security, idempotency rules, and retry math live here.
                 Easy to unit-test without any infrastructure.

  app/storage/   Thin wrapper around Redis. The rest of the app calls
                 this instead of talking to Redis directly, so the
                 Redis client is swapped out in tests without touching
                 business logic.

  app/workers/   Runs as a separate OS process alongside the API server.
                 Consumes from the Redis queue and drives actual delivery.

  tests/         One test file per concern (matches app/core/ modules
                 plus the health route). conftest.py holds fixtures
                 shared across all test files.

  demo/          A single static HTML page — no build step needed —
                 used for manual testing during development.

  .github/       CI config only. One workflow file that runs the test
                 suite on every push.
